## 0. 调研范围与取舍

上一轮只看了 README/VISION/oh-my-multica 方法论（产品层）。本轮钻进 `server/`（Go 后端，Chi + sqlc + WebSocket）的真实实现。选定以下 7 个**直接决定"多 agent 如何协作"** 的文件（其余 26+ 个 `pkg/agent/*.go` 是各 agent CLI 的适配层、属于"执行层"而非"协作决策层"，不在此分析）：

| 文件 | 角色 | 关键体量 |
|---|---|---|
| `server/internal/dispatch/reason.go` | 执行准入 taxonomy（封闭枚举） | 6KB |
| `server/internal/issueworkflow/issueworkflow.go` | 声明式工作流状态机 + 自动交接 + Brief 生成 | 30KB |
| `server/internal/daemon/reconcile.go` | daemon 侧幂等对账广播器 | 4.6KB |
| `server/internal/skill/frontmatter.go` + `skills-lock.json` | 技能元数据格式 + 哈希锁 | 2.7KB + 配置 |
| `server/internal/service/issue_trigger.go` | 派单决策纯函数 `WillEnqueueRun` | 9.7KB |
| `server/internal/service/task_claim_decision.go` | 认领决策的 SQL 栅栏 + 可观测性 | 8KB |
| `server/internal/service/agent_invocation.go` | 调用权限模型（fail-closed） | 2.6KB |
| `server/internal/service/task_triage_guard.go` | Triage 人类在环门 | 5KB |

## 1. 核心机制一：派单决策是一个"纯函数"，不是 LLM 经理（最有价值的发现）

`issue_trigger.go` 的 **`WillEnqueueRun`**（约 L80–200）是全局**唯一**的派单判定点：输入"一次 issue 写操作的事后形态"，输出"这次写会不会启动一个 agent run、由谁跑"。

它的设计原则直接打脸"让一个 AI 当项目经理决定下一步"的直觉：

- **单一真相源**：注释明确说它替换了之前 4 个互相漂移的派单入口（squad 漏判、self-loop 漏判，见 MUL-3375）。"写路径"和"预览接口"共用同一个函数，保证预览承诺的 run 与实际入队的 run 完全一致——**预览永远不会承诺一个写路径会丢弃的 run**。
- **多态指派（human + agent 统一）**：`AssigneeType` 是 `agent` 或 `squad`；squad 实际由 `LeaderID` 跑。这与 AGENTS.md 里"assignee 多态（assignee_id + assignee_type）"一致——人和 agent 在同一张看板上平等。
- **Backlog 是停车场，Triage 是拒绝门**：`currentStatus == "backlog"` 只 defer（ parked）不启动；而 Triage 直接 refuse（见 §5）。
- **去重靠 SQL 唯一索引**：`(issue_id, agent_id)` 对 pending 任务的 partial unique index。判定前的 `hasPendingRun` 镜像这个栅栏，**出错 fail-closed 返回 true（当作有 pending）**，绝不超额承诺。
- **self-loop 抑制**：一个 agent 把自己的 issue 移出 backlog 时，不会重新触发自己正在跑的 task。

**对 MemALL 的含义**：MemALL 的"经理"不该是 LLM，而该是 `goals.py` 里已有的**确定性 `next_action`/`goal_tick`**。Multica 用代码证明了"纯函数派单 + 唯一索引去重 + 失败即保守"这条路线可生产级收敛。MemALL 当前缺的是：① `goal_tick` 没接线（前几次分析已确认）；② 没有"多态指派"概念（MemALL 的 task 归属 agent，但人和 agent 的协作边界模糊）；③ 没有"派单决策单一纯函数 + 预览一致性"纪律。

## 2. 核心机制二：认领是"拉模型 + SQL 行级原子认领"，不是"推模型"

`task_claim_decision.go` 顶部注释揭示了真实认领机制（不是我们以为的"服务器推给 agent"）：

> 认领 SQL 栅栏：`wakeup gate` + `runtime liveness` + `per-(issue, agent) serialization` + `rebind fence` + 并发上限。

- **三条认领路径**（`claimPath`）：`agent`（agent 主动触发）、`runtime`（单机轮询）、`batch`（机器级批量）。
- **原子行认领**：daemon 轮询 → 候选查询已按 wakeup 有效性 + agent/runtime 绑定过滤 → 抢到行锁才执行。**这天然防双跑**。
- **整文件是"决策可观测性"**：把所有不可见的认领结果（`no_tasks`/`no_runtime`/`runtime_mismatch`/`no_capacity`…）收敛到一个封闭 reason 枚举，且"reason 只陈述证据支持的因果"（如 `no_visible_candidates` vs `candidates_unclaimed` 拆分，对应 #8551 队列等待归因）。

**对 MemALL 的含义**：① MemALL 若做 agent 自动认领，应走"拉模型 + 唯一索引/行锁去重"，不要推；② **决策必须可观测**——这正是我们前几次分析指出 MemALL 协作"无可见性"的病症的解药。MemALL 的 `goal_tick` 应像 `recordClaimDecision` 一样，对每次"为何这个 goal 没推进"产出结构化 reason。

## 3. 核心机制三：声明式工作流 + 自动交接 + 自动生成 Brief

`issueworkflow.go` 是一个完整、声明式的协作状态机：

- **Workflow = 流水线**：从共享 `issue_status` 目录选出有序状态；每个 step 带 `Handler`（`none`/`agent`/`squad`/`member`/`project_lead`/`creator`）。**进入带 handler 的 step = 自动交接（handoff）给该 handler 并启动 run**（约 L35–42, `ResolveHandler` L300）。
- **`Brief()` 自动生成 agent 读到的指令块**（约 L380+）：列出所有状态、每个 step 交接给谁、当前 step 的 instructions、下一步命令。**这就是 oh-my-multica 说的"确定性 Loop 拥有控制权"的代码实现**——环境（Harness）把"状态/交接/指令/退出检查"编码进 agent 的 prompt，agent 只消费信号。
- **`handlerlessSpan`（约 L230）** 解决"agent 把一件事拆成多列"的 bug（MUL-8231）：一段无 handler 的状态 = 同一 assignee 一口气干完，直到遇到交接 step 才转交。直接对应 MemALL `goals.py` 的"别把一个 goal 过度碎成子任务"。
- **`StepMovedError`（约 L410）** 防并发交接冲突：若别人在 run 工作时把 issue 移走，该 run 的状态变更被拒——"不要再次改状态，留评论"。这是协作的并发安全网。

**对 MemALL 的含义**：MemALL 的 `goals.py` 已有 `children` + `depends_on_idx` + `acceptance`/`verifier`，但**没有"进入某状态自动交接给某角色并生成该角色的指令 Brief"这种声明式 handoff**。可借鉴：给 goal 的 state 加 `handler`（agent/member/reviewer），进入该 state 自动把控制权交给对应角色并生成它的工作简报。

## 4. 核心机制四：准入 taxonomy + fail-closed 权限

- `dispatch/reason.go`：执行准入是**封闭枚举** `ReasonCode`：`queued`/`coalesced`/`steered`（把评论注入正在运行的 agent 的 turn）/ 一堆拒绝码（`runtime_offline` 任务不丢、等机器回来；`agent_runtime_required` 根本没有机器可回；`attribution_blocked` 失败即拒绝…）。关键铁律：**枚举绝不泄露私有 agent 是否存在/名字/owner**（`ReasonInvocationNotAllowed` 故意不区分"私有"和"不存在"）。
- `agent_invocation.go`：`CanMemberInvokeAgent` **fail-closed**——查询没回答就当"无权限"。三种权限模式：`private`（仅 owner）、`public_to`（workspace/member 目标）。读错误 = 拒绝，**绝不把瞬时 DB 错误变成"你没权限"**（把"不知道"和"拒绝"分开返回）。

**对 MemALL 的含义**：MemALL 若开放"agent 间互相派活"或"人对 agent 授权"，应直接抄这套 **fail-closed + 枚举不泄露存在性** 的纪律。`verify_goal` 当前只管"生产者不得验收"，应补一层"调用/授权是否合法"的 fail-closed 校验。

## 5. 核心机制五：人类在环（Triage 门 + Attribution）

`task_triage_guard.go`：**Triage ≠ Backlog**。Backlog 推迟 run；Triage 直接拒绝"从 issue 派生 executor"——因为 triager 还没决定谁干。规则精确：

- `OriginDerived`（系统从 assignee/squad/retry 推导 executor）→ **Triage 中拒绝**；
- `OriginNamed`（人亲手 @mention 某 agent）→ Triage 中**允许**（那是人与该 agent 的对话，成本是人选的）。

注释原话："Prefilling an owner is how a run starts today, and the triager must record its reasoning as a comment, so without this the triager would dispatch the very owner it was only proposing."

另外 `attribution_stamp.go`（68KB）贯彻"**每个 run 必须 stamp 一个负责任的人**，fail-closed 工作区若解析不出责任人就拒绝运行"。

**对 MemALL 的含义（关键差异化机会）**：MemALL 的 `goals.py` **没有"人类在环"状态**。建议给 goal 增加 `triage` 状态：goal 被创建/自动分解后先进 triage，**在人对 acceptance/verifier 确认前，agent 不得自动执行**；而人显式指派的任务（named）可立即跑。这既补了 MemALL 的安全短板，又正好区别于 Multica（Multica 的 human-in-loop 只在 issue 层，MemALL 可在 goal/知识层做更深的 human-in-loop）。

## 6. 核心机制六：幂等对账（reconcile.go）

`daemon/reconcile.go` 的 `reconcileBroadcaster`（约 L20–130）：

- **边沿触发 + 单槽重放**：WS 断开重连后，服务器在间隙改的状态，daemon 的各慢轮询（5s 取销轮询、30s 工作区同步）立刻被"broadcast"唤醒重查，不打乱 ticker 节奏。
- **防抖**（1s）：抖动的网络重连不会变成 GetTaskStatus 风暴。
- **启动竞态闭合**：晚到的订阅者能恰好补看到错过的那次 broadcast（replay flag）。

`workspaceChangeSignal`：单消费者脏标志，1 槽缓冲，把突发合并成一次对账。

**对 MemALL 的含义（直接验证我们之前的建议）**：我们前几次分析建议"把 `goal_tick` 做成 idempotent + reconcile"。Multica 用生产级代码证明了这个模式——**重跑从对账开始、context 重置也不丢进度**。MemALL 的 `goal_tick` 应读当前 goal 快照 → 决定前进/返工/停/请求人审，**幂等且可重入**。这是被双重验证的最小改动。

## 7. 核心机制七：技能模型（极简 + 哈希锁）

- `skill/frontmatter.go`：`ParseSkillFrontmatter` 只从 SKILL.md 的 YAML frontmatter 抽 `name` + `description`；值与 TS 侧 `parseFrontmatter` 逐字段对齐（两边对同输入一致）；自动 trim 尾部换行（修 MUL-5645 导入差异 bug）。**技能 = 一个 SKILL.md 文件 + frontmatter，极简、可移植**。
- `skills-lock.json`（仓库根）：`{ skills: { <name>: { source, sourceType: "github", computedHash } } }`——**技能从 GitHub 仓库按 commit hash 锁定拉取**，像 lockfile 一样防漂移。

**对 MemALL 的含义**：MemALL 要建"技能层"（前几次分析列为 P0），**直接抄这两样**：① SKILL.md frontmatter 格式（name/description）；② 哈希锁 lockfile 模式。这比自己发明格式省事且已被 53k 星项目验证。

## 8. 机制级映射总表

| Multica 机制（代码位置） | MemALL 现状 | 借鉴动作 | 优先级 |
|---|---|---|---|
| 派单纯函数 `WillEnqueueRun`（issue_trigger.go） | 无单一派单点；协作靠 agent_round 提醒 | 把 goal 推进收敛成单一 `goal_tick` 纯函数，写/预览共用 | **P0** |
| SQL 行级原子认领 + 三路径（task_claim_decision.go） | task 认领在内存态，无去重栅栏 | agent 认领走"拉模型 + 唯一索引/行锁去重" | P1 |
| 决策可观测封闭 reason 枚举（task_claim_decision.go） | 协作无可见性 | `goal_tick` 每次产出结构化 reason（为何没推进） | P1 |
| 声明式 handoff + `Brief()`（issueworkflow.go） | goals 有 state 但无"进入即交接+生成简报" | 给 goal state 加 handler，进入即交接并生成该角色 Brief | P1 |
| `handlerlessSpan` 防过度碎裂（issueworkflow.go） | 子任务可能过度拆分 | goal 分解时合并"无 handler 的连续状态"为同一 run | P2 |
| `StepMovedError` 并发安全（issueworkflow.go） | 无并发交接冲突防护 | 若多人/agent 同时改同一 goal，后者变更被拒并留评论 | P2 |
| fail-closed 准入 + 不泄露存在性（reason.go / agent_invocation.go） | verify_goal 只管非生产者验收 | 补 fail-closed 授权校验；枚举不泄露私有 agent 存在 | P1 |
| Triage 人类在环门（triage_guard.go） | 无 human-in-loop 状态 | goal 加 `triage`：确认 acceptance 前 agent 不自动执行 | **P0** |
| Attribution 责任人 stamp（attribution_stamp.go） | 无"谁负责"概念 | 每个 goal/run 绑定责任人（fail-closed） | P1 |
| 幂等对账（daemon/reconcile.go） | goal_tick 未接线 | `goal_tick` 做成 idempotent + reconcile（重读快照再决策） | **P0** |
| SKILL.md frontmatter + 哈希锁（skill/ + skills-lock.json） | 无技能层 | 技能格式直接采用；建 skills-lock 式 lockfile | **P0** |

## 9. MemALL 相对 Multica 的已有优势（别反向抄错）

1. **非生产者验收**：MemALL `verify_goal` 强制"生产者不得验收" + `returned` 回退。Multica 核心是 handoff 链（下一步 handler 验收），**没有显式"生产者≠验收者"纪律**，要靠 oh-my-multica 补。MemALL 这条更强，应保留并声张为卖点。
2. **持久记忆是 MemALL 的护城河**：Multica 本质是"执行事件记录层 + 控制面"（run log、runtime 管理、26 个 agent 适配），**几乎没有跨任务持久化的"知识/记忆"层**。这正是 MemALL 的 L1–L11 记忆体系的主场。二者互补，不是竞品。
3. **goal 驱动协作状态机已建待通电**：`goals.py` 的 `next_action`/`goal_tick` 与 Multica 的确定性派单思路同源，方向正确——只差接线。

## 10. 边界：什么绝对不该抄

- **不要重建控制面**：Multica 的 daemon（474KB 单文件）、WS 协议、runtime 管理、26 个 agent 适配器、Kanban UI 是千万行级工程。**MemALL 定位是"记忆 + 目标协作 OS"，抄这些等于自杀式偏离**。只借其协作决策范式，不借其执行后端。
- **许可证**：Multica 是 source-available（Apache-2.0 + 附加条款，**非标准 OSS**），代码**只可研究不可直接复用**。oh-my-multica（MIT）的方法论可自由参考。
- **benchmark 自报非独立验证**：对外口径谨慎。

## 11. 结论与下一步建议

Multica 用生产级代码验证了三条我们之前"靠推理建议"的结论：
1. **经理该是确定性状态机 + SQL 栅栏，不是 LLM** —— `WillEnqueueRun` + 原子认领就是样板；
2. **幂等对账（reconcile）是对的** —— `goal_tick` 必须 idempotent + reconcile；
3. **人类在环（Triage）+ 责任人归因（Attribution）是协作系统的安全底座** —— MemALL 当前缺这块。

**最小改动、最大收益的 3 件事（均已在 MemALL 代码中有落点）**：
- **P0-①**：`agent_round()` 末尾接 `goal_tick()`，并做成 idempotent + reconcile（呼应 Multica reconcile.go）；
- **P0-②**：给 `goals.py` 加 `triage` 状态 + 责任人字段（呼应 Multica triage_guard + attribution）；
- **P0-③**：建技能层，直接采用 SKILL.md frontmatter + skills-lock 哈希锁格式（呼应 Multica skill/ + skills-lock.json）。

需要我直接动手做 P0-①（给 `agent_round` 通电 `goal_tick` 并加 reconcile）吗？这是被 Multica + oh-my-multica 双重代码验证、且 MemALL 已有 `goals.py` 骨架的最小一步。
