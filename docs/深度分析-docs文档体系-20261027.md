## 2. 对《深度分析-多Agent协作梳理》的核验：2 处事实错误

它批评我的《重新梳理》，我逐条核验，**接受 2 条、驳回 2 条**。

### 2.1 错误一：「文档漏了 goals.py，所以重复造轮子」——时间线不成立

它说：

> dsh 在 §2.1「已具备」与 §2.2「关键缺口」里**完全没提 `pipeline/goals.py`**……

核验：

```
docs/重新梳理-多Agent自动协作-20261027.md  提交 f183456  10-27 21:22
src/memall/pipeline/goals.py               提交 0ff0f76  10-27 22:57
```

**我的分析文档提交时，`goals.py` 还不存在。** 是我在 21:40 左右、按老陈"要能自动拆解并论证分配"的明确要求新写的，22:57 才提交。

它把"我之后的实现"拿去否定"我之前的分析"，得出"重复造轮子"的结论。这不是事实分歧，是**它读了共享文件系统上的未提交文件，却当成既有代码**。

### 2.2 错误二：「`goal_tick` 全仓无任何运行时调用点」——事实错误

它说：

> `goal_tick`（`goals.py:482`）**只被定义，全仓无任何运行时调用点**（grep 确认：无 scheduler / agent_round / fallback / cron 调用；MCP 层…**未暴露 `goal_tick`**）

核验：

```
src/memall/pipeline/fallback.py:160   from memall.pipeline.goals import goal_tick
src/memall/pipeline/fallback.py:162   tick = goal_tick()
src/memall/pipeline/fallback.py:197   goal_result = deliver_goal_prompts()   # 每个 tick 都跑
src/memall/mcp/tools/goals_handlers.py:86   return _dumps(goal_tick(conn))   # goal_status 无 goal_id 时
```

`goal_tick` **已经通电**：挂在常驻的 fallback 定时器上（每 tick 都跑，不是只在有 distill 工作时跑），并已通过 `memall_read action=goal_status` 暴露。它的 grep 结论是错的。

### 2.3 它说对的一条：`agent_round` 确实没调 `goal_tick`

但**这是有意的**：`agent_round` 唯一调用方是 `scheduler/scheduler.py:112`，而**调度器进程根本没在跑**（本会话多次实测）。把驱动器挂到 `agent_round` 等于挂到一个死进程上；挂 fallback（MCP 进程内常驻）才是对的。

所以"应把 goal_tick 接进 agent_round"这条建议**方向是反的**——它把一个活着的钩子挪到一个死掉的进程里。

### 2.4 它对的地方（应记一功）

> §4.2 统一两套验收语义：goals 体系强制非生产者验收；裸 L5 task 的 `resolve_task` 用 `_caller_gate`，**允许归属 agent 自己关闭**，无 verifier 概念。

核验属实：

```
task_lifecycle.py:72   if _addressed_to(meta, row_agent_name, caller) or _is_supervisor(caller): return None
```

即**生产方可以自己关自己的卡**。而 `goals.py:verify_goal` 对生产方返回 `forbidden`。

**同一个系统里，`resolve_task` 允许生产方自验、`verify_goal` 禁止。这是真实的不一致**，也是全篇最有价值的一条发现。

## 3. 体系性问题（比单份文档的错误更重要）

### 3.1 ADR 停摆：86 个提交、0 份 ADR

```
ADR 最后更新：2026-10-02
此后提交：86 个
```

而按 `ADR/README.md` 自己定的门槛——"影响数据模型/写入语义/对外契约"、"修掉根因级缺陷并改变既有行为"、"多个合理方案选定其一"——这 5 周里**至少 8 个决策该写 ADR**：

| 决策 | 为什么够门槛 | 现状 |
|---|---|---|
| L5 任务卡 + claim + assignee | 改变写入语义，新增对外契约 | 无 ADR |
| `metadata.pinned_fields` 钉住机制 | 改变分类器行为，data-model 级 | 无 ADR |
| 会话级身份绑定（F3） | 改变对外契约（env/握手） | 无 ADR |
| 通知栏三传输合一 | 统一对外行为 | 无 ADR |
| 收敛门（action_item 未表态不收敛） | 改变会审语义 | 无 ADR |
| 目标生命周期（intake→closed） | 全新对外契约 | 无 ADR |
| 依赖门（depends_on 强制执行） | 改变认领语义 | 无 ADR |
| 生产者不得验收（§五 落地） | 改变验收契约 | 无 ADR |

**后果已经发生了**：WorkBuddy 之所以会误判"goals.py 该不该存在""goal_tick 有没有通电"，正是因为**没有 ADR 告诉它这些是什么时候、为什么加进来的**。ADR 停摆不是因为懒，是因为叙事型文档替代了它——而叙事型文档会漂移。

## 4. `OpenSpace 调研`的可靠性

**做得好的**：它读了 `evolver.py` 源码而非只看 README，区分了"实证"与"摘要"；诚实标注 Benchmark 是 HKUDS 自报未经独立验证；明确说"别抄它的执行后端"。

**一个未验证的比较**：

> OpenSpace「**无多 agent 目标协作状态机**」…「goals.py 有 intake→…→closed + 非生产者验收（OpenSpace 没有）」

这个"没有"只从 `evolver.py` 推出，**没有验证 OpenSpace 是否有独立的任务/编排模块**（它声称支持 MCP server + 多宿主，编排可能在外层）。把一个"未验证的缺失"当成"差异化护城河"写进对外话术是有风险的——这正是 ADR-0001 想防的那类漂移，只是换了领域。

**建议**：对外话术里把"OpenSpace 没有"改成"我们未在其公开源码中找到"，保持可证伪。

## 6. 一句话总评

**这套文档的问题不是写得差，是"没有新陈代谢"。**

有五份 ADR 写得像教科书（背景带数据、决策可测、后果分正负、验证指向测试），然后这套实践停摆了五周，期间 86 个提交、8 个够门槛的决策零记录；同时四份叙事文档在互相覆盖且互不引用，最新的一份还因为读了未提交的代码而误判了另一份。

**修法不是写更多分析，是恢复 ADR 这个新陈代谢机制，并给旧文档标上失效。**
