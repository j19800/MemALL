## 三、我的看法：它诊断错了瓶颈，而"药方"会做无用功

原报告给的四个方案，**方案 2（常驻 Gateway + Heartbeat）被它自己定为通用性最优**。我认为那是**错的投资方向**，理由都在我们的实测数据里。

### 3.1 心跳的成本模型对 MemALL 是负的

心跳模式的本质是：**定时叫醒 → 花 token 问"有活吗" → 多数时候答"没有"**。

原报告 §六.1 自己也承认："心跳/定时唤醒每次醒来都产生 LLM 调用费用，即使无事可做。"

而 MemALL 现在的 `goal_tick` 是 **状态驱动的确定性计算**：
- 每 300s 跑一次，**零 LLM 成本**（纯 DB 查询）
- 只有**确实存在下一步动作**时，才 spawn 一个 agent

也就是说：**"事件驱动、空闲零成本"这个目标，MemALL 用另一种方式已经达成了**。再叠一层 heartbeat，等于在免费的轮询之上再买一份收费的轮询。

### 3.2 就算建了 gateway，也只能唤醒 2/5 的 agent

我 10-30 逐个查过（见 `docs/DeepSeekCLI-接入our-free-model-20261029.md` §唤醒能力矩阵）：

| agent | 有无自己的非交互入口 |
|---|---|
| dsh | ✅ `--profile headless` |
| opencode | ✅ `run` |
| Qoder CN | ❌ 单一大 exe，`resources\bin` 只有原生 node 模块 |
| WorkBuddy | ❌ 只有 pty/vendor 脚本 |
| Trae CN | ❌ `bin\trae-cn.cmd` 是 VSCode 打开文件的 CLI，不是 headless agent |

**gateway 再强，也没法叫醒一个没有"耳朵"的 agent。** 三个 GUI agent 的正确通道是任务卡 + 定向会话通知（我们已实现，跨进程可达）。

### 3.3 真正卡住闭环的不是"唤醒"，是这两条

1. **§五 独立验收 vs 可唤醒 agent 数量**
   `producers = 各子任务执行者 ∪ 目标 owner`，验收人不得是生产者。只有 2 个可唤醒 agent 时：
   - 两人都产出 → 两人都是生产者 → **没人能验收**
   - 想跑通全自动，只能一人全包、另一人验收 —— **那不叫分工**
   - 真分工 + 自动验收，**必须第 3 个可唤醒 agent**

2. **拆解质量**
   实测中有一次唤醒后交出的计划是：`[0] 测试标题`（单条、占位内容）。门禁全放行（单子任务不触发依赖契约）。**加更多唤醒次数不会改善这一点**，反而放大垃圾产出。

这两条，heartbeat 一条都解决不了。

### 3.4 厂商通道（方案 1/3）不该碰

- `claude/channel`：要求 Claude Code 会话**保持打开** + 显式注册 + 企业策略开关，事件 fire-and-forget、**会话关闭静默丢**；且只适用 Claude Code。本机 **Claude Code 没装**（我们要用的是 dsh/opencode）。
- Claude Agent SDK 事件 API：同理，且要求常驻会话——又回到"需要一个 runtime"，而这个 runtime 我们现在用 `dsh --profile headless` 已经解决了。

**投入产出比为负。**

## 四、真正值得借鉴的三条（有具体动作）

### 4.1 渐进自主等级（Graduated Autonomy）——直接可用

原报告 §设计原则 2 给了 Level 0–3。这恰好是我们 `agents.wake` 配置缺的**表述与安全台阶**：

| 等级 | 语义 | 对应现有配置 |
|---|---|---|
| L0 | 完全被动 | `enabled=false` |
| L1 | 只记录不执行 | `enabled=true, dry_run=true` |
| L2 | 白名单 agent 可执行 | `commands` 只配可信 agent + `max_per_hour` 收紧 |
| L3 | 全量自主 | 全部配齐 + 放开配额 |

**收益**：把"敢不敢开"从二元开关变成四级台阶。这是给运维/老陈看的安全叙事，成本几乎为零（现有字段已经支持，只需文档化 + 一个 `autonomy_level` 便捷字段）。

### 4.2 决策可观测（Observable Decision-Making）——修一个真实缺陷

原报告强调"每次自主行动都要留推理痕迹"。这正好命中我已知的一个缺陷：

> `agent_waker` 的审计日志 `_wake_log` 是**进程内内存**，驱动脚本一退出证据就没了。

10-30 排查"唤醒了但没推进"时，我就是因为没有持久化审计，只能手动重放一次 dsh 才看到 agent 的推理过程。**这条该修**：把 `wake_log` 落库（复用 `session_notes`/新表都行），字段含 agent / goal / action / argv 摘要 / rc / stdout 尾部 / 触发原因。

**收益**：可追溯 + 可复盘 + 满足"一键停用前先看得见发生了什么"。这是我列的 MemALL 真实缺陷里性价比最高的一条。

### 4.3 持久化状态 / 断点恢复——我们已有 80%，缺最后 20%

原报告 §六.4 说 cron 唤醒是全新会话、必须落盘状态（Hermes 的 `HEARTBEAT.md` / `current-state.md`）。

MemALL 的结构优于它：**目标元数据本身就是状态机**（phase / plan / phase_history / verdict 全在 `memories.metadata` 里），新会话读 `goal_status` 即可恢复，不需要额外状态文件。

**缺的 20%**：**在途唤醒的崩溃恢复**。如果 dsh 进程被 kill 或超时，`wake_claims` 里会留一条 claim，冷却期内不会再唤醒（幸而是 fail-closed，不会双跑）。但也没有"上次唤醒失败了，升级处理"的机制。原报告 §六.5 提到的"错过运行补偿"，我们是**天然具备**的（状态驱动，下次 tick 自然补上），这一点反而是我们比 cron 方案强。

### 4.4 一条我不同意它、反而要坚持的

原报告 §五方案 2 把它自己定位为"通用性最优"。我认为**通用性在这里不是优点**：它的通用性来自"把 agent 当黑盒，用一条 prompt 敲门"。而 MemALL 的 `_inject_session_context` 是把**结构化状态**（待办、目标阶段、讨论）注入 `_meta`，agent 拿到的是数据不是自然语言猜测。

**黑盒敲门 > 结构化注入** 这个假设是错的。我们该做的是把结构化注入做得更完整，而不是退回成 prompt 敲门。

## 六、一句话总结

**这份调研的"外部世界"部分可信（85–90%，我逐条验到 npm/URL/源码级），但它对 MemALL 的诊断已经落后一天，且药方（gateway+heartbeat）会在一套已经免费且状态驱动的架构上做重复投资。**

它真正的价值不是"告诉我们缺什么"（它说错了），而是：
1. **外部印证了我们的架构选择是对的**——"事件驱动、空闲零成本"我们已用确定性 tick 达成，比 heartbeat 便宜；
2. 给了我们**渐进自主等级**这套安全语言；
3. 提醒我们**审计必须持久化**（这条是真缺陷，该立刻修）。
