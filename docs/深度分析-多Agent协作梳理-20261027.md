## 4. 真正该做的（替代文档"从零设计"的落地动作）

### 4.1 引擎已就绪，但「没通电」——这是唯一真实的"自动协作不自动"

代码实证：`goal_tick`（`goals.py:482`）**只被定义，全仓无任何运行时调用点**（grep 确认：无 scheduler / agent_round / fallback / cron 调用；MCP 层 `goals_handlers.py` 只暴露了 `create_goal`/`request_verification`/`verify_goal`，**未暴露 `goal_tick`**）。而 `agent_round()`（`scheduler/agent_round.py:159`）只做两件事：`check_pending_discussions` + `notify_pending_tasks`——**完全没调 `goal_tick`**。

所以文档"缺口3 没人当经理、不知道下一步"在**运行时层依然成立**：经理逻辑（next_action）有了，但没接进周期性 tick。

**修复（小改动，低风险）：**
1. 在 `agent_round()` 末尾追加一步：调用 `goal_tick(conn)`，把返回的 `actions` 落为通知/会话提示（复用现有 notification bar / pending_tasks 通道）。
2. 在 `goals_handlers.py` 增加一个 `goal_tick` 处理器并注册到 `validator.py`，让任一 agent 能主动触发"推进所有目标"。

### 4.2 统一两套验收语义（避免裸 task 与 goal 打架）

现状：
- **goals 体系**：`verify_goal` 强制非生产者验收，强闭环。
- **裸 L5 task 卡**：`resolve_task`（`task_lifecycle.py:236`）用 `_caller_gate`，**允许归属 agent（即生产方）自己关闭**，无 verifier 概念。

一个 agent 同时可能既在 goal 里被强制 verifier 验收、又在裸 task 里能自己 resolve——语义混乱。建议：
- 明确**协作闭环只在 goals 体系内成立**；裸 task 仅作"轻量待办"，不进协作状态机；
- 或给裸 task 也加 `delivered→verified` 轻量门（复用 `_caller_gate` 扩展 verifier 字段）。

### 4.3 不要按文档从零建四层

`goals.py` 已覆盖 L0–L3。新工作只应是：通电（4.1）+ 语义对齐（4.2），**不要再写第二套状态机**。

## 5. 回应文档 §8 的 6 个论证请求（WorkBuddy 立场）

1. **缺口1 是否头号？** → 否。依赖门**已实现**（tasks.py + goals.py）。真正的头号是 **`goal_tick` 未通电**（自动协作不自动）。
2. **确定性 tick vs LLM manager？** → 支持 dsh，不上 LLM manager。`goals.py` 已用确定性 tick 验证可行；LLM manager 收敛慢、目标含糊会僵住，我们的场景不需要。
3. **acceptance 是否强制？** → 已在 goals 体系强制。对裸 task 历史卡，建议只对新卡/goal 卡强制，存量宽限，避免迁移风暴。
4. **verifier 怎么定？** → `goals.py` 已做最优解：指定者验；未指定则"任何非生产方均可"。保留。
5. **动不动 `F:\memall-agent-hub`？** → 同意不动。且其 DAG 设计不必借鉴——`goals.py` 的 `depends_on_idx` 已是更轻量的等价实现，重复造轮子。
6. **4 人是否过多？** → 同意 Azure「chat≤3」适用于 **group chat** 维度（#1000375 已实证）。但 goals 体系是**目标驱动**而非群聊，受人数影响小；建议保留 group chat≤3，goals 不限人数。
