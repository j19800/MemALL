# 重新梳理：MemALL 多 Agent 自动协作该怎么做

> 作者：dsh ｜ 日期：2026-10-27
> 缘起：老陈要求"重新梳理思路，可全网搜索借鉴相关项目"
> 方法：外部权威源（Azure 架构中心的多 Agent 编排模式、arXiv 2501:06322 协作机制综述）+ 对 `E:\MemALL` 活库与源码的实测盘点
> 立场：**推翻"再加一条通道"的路线**。我们缺的不是通道，是三个契约。

---

## 0. 一句话结论

**我们已经把"通信"做完了，但没把"协作"做出来。**

通信 = 消息能到达（已完成：通知栏、memall_msg 总线、session note）。
协作 = 一件工作能**从谁开始、按什么顺序、由谁验收、卡住了谁负责**（未完成：依赖不强制、验收靠自觉、无人决策下一步）。

外部成熟方案（Azure 五模式）里，MemALL 现在同时是 **Group chat**（讨论收敛）和**残缺的 Handoff**（任务卡），而 Handoff 之所以"残缺"，是因为缺三件事：**依赖没强制、验收没闭环、没人当经理**。

---

## 1. 外部方案给的坐标系

### 1.1 Azure 架构中心：五种编排模式（2026-02 更新）

| 模式 | 协作方式 | 路由 | 适合 | 坑 |
|---|---|---|---|---|
| **Sequential** | 线性流水，上一个的输出是下一个的输入 | 确定性预定义 | 步骤有明确依赖的渐进精化 | 前段失败向后传播；无并行 |
| **Concurrent** | 多 agent 同时处理同一输入，结果聚合 | 确定或动态选择 | 多视角独立分析、时延敏感 | 结果矛盾需冲突解决；资源密集 |
| **Group chat** | 共享会话线程，chat manager 控制发言顺序 | manager 控制轮次 | 共识、头脑风暴、**maker-checker 验证** | 对话循环；超过 3 个 agent 难以控制 |
| **Handoff** | 动态委托，**同一时刻只有一个活跃 agent** | agent 自己决定何时移交 | 处理中才逐渐明确该找哪个专家 | 移交死循环；路径不可预测 |
| **Magentic** | **manager 构建并持续修订任务账本（task ledger）**，包含目标与子目标，动态增删改序 | manager 动态分配 | 开放式、无预定解法的问题 | 收敛慢；目标含糊时会僵住 |

三条来自同一篇文章、对 MemALL 直接适用的原则：

1. **"用能可靠满足需求的最低复杂度"**——多 agent 会引入协调开销、时延与新的失败模式，必须能被"单 agent 做不到"证明。
2. **"把共享状态持久化到外部存储"**，并"在 HITL 检查点持久化以便恢复而不重放"。
3. **反模式清单里有一条正是我们踩过的**："在并发 agent 之间共享可变状态，会因假设跨 agent 边界同步更新而导致事务不一致。"

### 1.2 arXiv 2501.06322（协作机制综述）的五维框架

`actors`（谁参与）· `types`（合作/竞争/竞合）· `structures`（点对点/集中/分布）· `strategies`（角色驱动/模型驱动）· `coordination protocols`（协调协议）。

它把"协作"拆成"结构 + 策略 + 协议"三层，而不是"消息格式"。这与我们的教训一致：**协议层我们早就有了（MCP），出问题的一直是结构与策略。**

## 2. 现状盘点（实测，不是回忆）

### 2.1 已具备（这部分不必重做）

| 能力 | 实现 | 状态 |
|---|---|---|
| 记忆总线 | SQLite + FTS5 + vec0 + L1–L11 分层 | 生产运行，4000+ 条 |
| 任务卡 | L5 + `category=task` + `metadata.assignee` + `status` 状态机 | 可用，守卫覆盖 |
| 认领 | `memall_write action=task_claim`，非归属者返回 `forbidden` | 可用 |
| 送达 | 通知栏（`mcp/notify.py`，每次响应实时查，带 `[ID\|标题\|状态]`） | 可用 |
| 实时通道 | `memall_msg`（总线已接回主库） | 可用 |
| 讨论会审 | `participants` + `convergence_rule`（unanimous/majority/any）+ action_item 门 + timeout | 可用 |
| 定时提醒 | `agent_round.notify_pending_tasks` | 可用（终态会关闭提醒） |
| 身份 | `session_identity`（握手 / `MEMALL_AGENT_NAME`） | 可用，**需每个客户端配置** |

### 2.2 关键缺口（实测确认）

**缺口 1：`depends_on` 只是摆设**

`federation_tools.py:261` 把 `metadata.depends_on` 读出来**展示**，但 `mcp/tasks.py` 里**完全没有 `depends_on`**——`claim_task` 不检查前置依赖。

**实测证据**（2026-10-27，活库）：

```
A=1000654 (status=active 未完成)  B=1000655 (depends_on=[1000654])
B 落库的 depends_on: [1000654]
认领 B 的结果: {"status": "claimed", "claimed_by": "dag_probe", ...}
→ ❌ 前置 A 未完成，B 仍被成功认领 —— depends_on 完全没被校验
```

后果：**任何 agent 可以在前置任务没完成时就认领下游任务。** 这不是"协作"，只是"并行"。

**缺口 2：验收没有闭环**

终止转移只有 `resolve_task`（写 `status=resolved`、`arc_status=closed`）。没有任何强制"另一个 agent 验证"的路径。§五 写了"验收方 ≠ 生产方"，但**代码不强制**——`resolve_task` 可以由 assignee 自己调，谁调谁算完成。

后果：交付物质量只能靠自觉。

**缺口 3：没有"决策下一步"的角色**

`agent_round` 只做三件事：列出活跃 agent、给每个人生成提醒、跑一轮。**没有人计算"现在整个项目最该做的是哪一件"**。

现在的"自动"实质是"每个人各自被提醒有一堆待办"，不是"系统知道下一步"。

**缺口 4：没有依赖图结构**

无 `task_edges` / `blocked_by` 表或字段（只有 metadata 里的 `depends_on` 数组，且不校验）。所以无法回答"这个项目还剩哪条链没走完"。

## 3. 映射：MemALL 落在哪、缺哪块

| Azure 模式 | MemALL 对应 | 成熟度 |
|---|---|---|
| Sequential | 几乎没有（任务链未强制） | ✗ |
| Concurrent | 有（多 agent 并行各干） | △ 无冲突解决 |
| **Group chat** | **讨论会审已实现**（含收敛规则、maker-checker 的雏形） | ○ 可用 |
| **Handoff** | **任务卡 + claim + 通知**（但依赖不强制、验收不闭环） | △ 残缺 |
| **Magentic** | **完全没有** | ✗ |

**结论：我们该补的不是 Concurrent/Sequential，而是把 Handoff 补完，再在上面加一个最小的 Magentic 账本。** Group chat 已经够了（甚至 Azure 建议 chat 不超过 3 个 agent，我们 4–5 个已经开始出现收敛问题，实测 #1000375 的教训）。

## 4. 重新设计：四层，每层一个契约

设计原则：**不加新框架、不加第二个存储、每个契约都能被一条守卫断言。**

### L0 账本（Ledger）——不新建表，就是现有的 L5 任务卡

Magentic 模式的核心是 "task ledger"，但我们**已经有**了：L5 任务卡 + `depends_on` + `status`。缺的只是"把它当账本用"。

- 账本 = `SELECT * FROM memories WHERE level='L5' AND category='task'`
- 依赖边 = `metadata.depends_on: [task_id, ...]`（已存在，只是不校验）
- **不引入 workflow DSL、不引入 DAG 引擎** —— Azure 明确说先用最低复杂度

**契约 1：一条任务卡必须能回答四个问题**：做什么（`content`）、谁做（`assignee`）、做完什么样（`acceptance`）、依赖谁（`depends_on`）。
缺 `acceptance` 的卡**不允许进入 ready 集**——这是"可验收"的物理前提。

### L1 就绪集（Ready）——把 `depends_on` 变成硬门

```python
def ready_tasks(agent_name) -> list[dict]:
    # active + assignee==me + 所有 depends_on 的卡 status 属于终态
```

- `claim_task` 前置校验：`depends_on` 里有任何一张卡不是 `done/resolved/archived` → 返回 `blocked_by`，**不允许认领**
- 通知栏只列 ready 的卡；被依赖挡住的卡显示为"等待 #N"

**契约 2：认领即承诺前置已完成。** 违反时必须显式失败（`blocked_by`），不能静默。

这是把"并行"变成"协作"的那一刀。**没有它，后面所有东西都是锦上添花。**

### L2 派工（Dispatch）——一个最小的 manager，但只做三件事

不加"会思考的 manager agent"（那是 Magentic 里最贵、最容易僵住的部分）。用一个**确定性的 tick** 而不是 LLM 决策：

```
每个 tick：
  1. 找出 ready 但没有 assignee 的卡 → 按能力匹配派给在册 agent（复用已有的 agent_routing.suggest_participants）
  2. 找出 active 且超期未认领的卡 → 升级提醒（已有 timeout 机制可复用）
  3. 找出 claimed 但长期无进展的卡 → 标记为 stalled，推给派单方
```

- 全部是**幂等**的：同一状态跑两遍结果相同
- **一次只改一个 agent 的状态**（Azure 反模式：并发改共享可变状态）
- 挂在已有的 fallback 定时器上（已常驻，不新增进程）

**契约 3：每张卡在任何时刻只有一个明确的"当前负责人"**（`assignee` 未认领时是承诺方，`claimed_by` 认领后是执行方，`verifier` 交付后是验收方）。三者不重叠。

### L3 验收（Verify）——把 §五 从"要求"变成"状态机"

现在 `resolve` 一按就 closed。改成：

```
active → claimed → delivered → verified → archived
                        └→ returned（打回，回 active）
```

- `delivered`：执行方交，写 `delivery` 正文
- `verified`：**必须由 verifier（≠ claimed_by）** 调用，写 `verdict`
- `returned`：verifier 打回，带 `correction`，卡回 `active` 且 `claimed_by` 保留（知道是谁的）

**契约 4：`delivered` 不能直接变 `verified`。** 没有这一步，"验收"永远是纸面要求——这正是我们发生过的事：`resolve_task` 谁都能调。

## 5. 明确不做什么（这一节同样重要）

| 不做 | 理由 |
|---|---|
| 自建通用 DAG / workflow DSL | Azure：用最低复杂度；我们只需要"前置完成才可认领"这一条谓词 |
| 第二个记忆库 | `F:\memall-agent-hub` 的教训：它自带 memory_store，与 MemALL 重复，边界不清，6 月停摆 |
| 把实时总线当主通道 | 总线是**时延优化**（~10ms），不是协作前提；通知栏已能拉式送达 |
| 用 LLM 当 manager 决策下一步 | Magentic 模式"收敛慢、目标含糊会僵住"；确定性 tick 已经能覆盖我们的场景 |
| 让 4+ agent 进同一个 group chat | Azure 明确建议 chat 不超过 3 个；我们 4–5 个已实测出现"9 分钟收敛、前置未交付" |
| 新增"提醒表"这类旁路状态 | 已经踩过三次：提醒表无读者、陈旧提醒永久静音、11 张孤儿卡 |

## 6. 落地顺序（按"能不能被断言"排序）

| 序 | 项 | 为什么排这 | 验收（守卫） |
|---|---|---|---|
| 1 | `depends_on` 硬门（L1） | **唯一能把并行变成协作的一刀** | `claim_blocked_by_dependency`：前置未完成 → claim 返回 `blocked_by`；前置完成后可 claim |
| 2 | 任务卡强制 `acceptance`（L0） | 没有验收标准的卡不可验收 | `task_card_requires_acceptance`：缺 acceptance 的卡不进 ready 集 |
| 3 | 验收状态机（L3） | 把 §五 从纸面变代码 | `delivered_cannot_self_verify`：claimed_by 自己 verify → 拒绝 |
| 4 | 确定性 dispatch tick（L2） | 让"下一步"有答案 | `dispatch_is_idempotent`：连跑两次状态不变 |
| 5 | stalled 升级 | 卡住能被发现 | `stalled_task_escalates` |
| 6 | 能力匹配派工 | 人在环时的效率优化 | `suggest_participants`（已存在，扩展任务场景） |

前 3 项是**协作的地基**，后 3 项是效率。**如果只做一件事，做第 1 项。**

## 7. 与外部方案的差异（我们该保留的独特处）

借鉴不等于照抄。MemALL 有几处是 Azure 五模式没覆盖、而我们有真实价值的：

1. **任务卡就是记忆**——不是外挂的 workflow state，而是可检索、可蒸馏、可继承的记忆。这让"上次类似任务怎么做的"能被召回，Azure 的模式里没有这层。
2. **验收结论沉淀为 L9/L10**——maker-checker 的"checker 意见"在别处是一次性文本，在我们这儿会被蒸馏进顶层知识。
3. **跨会话的身份与任期**——`session_identity` + `identities` 让"谁在什么时候做了什么"可追溯，长于单次编排的生命周期。

这三条是"记忆即总线"的实质，**不该为了对齐 Azure 的模式而丢掉**。

## 8. 请其他 agent 论证的点

1. **缺口 1 是否真是头号问题**？还是"验收没闭环"更致命？（我的判断：依赖门优先，因为它决定能不能并行；验收决定质量，但不阻塞流转。）
2. **确定性 tick vs LLM manager**：我主张不上 LLM manager。反驳条件：能举出我们场景里"必须靠判断才能决定下一步"的实例。
3. **`acceptance` 是否该强制**：强制会让存量卡全部不可用（需要迁移）。是不是应该只对新卡强制 + 存量宽限？
4. **验收人怎么定**：`verifier` 是派单方指定、还是按能力自动匹配、还是"任何非 owner 都可以"？
5. **要不要动 `F:\memall-agent-hub`**：我倾向不动（它有自己的 memory store，边界冲突）。但它有 DAG + scheduler 的现成实现，是否值得只读借鉴它的 `task_edges` 设计？
6. **4 人是否过多**：Azure 建议 chat ≤3。我们 4 个 agent 是否有 agent 实际没产出？要不要缩到 3？
