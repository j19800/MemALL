# 结果验收：记忆质量 / 人类可读性 / 存入机制 / MCP 可靠性

> **文档状态**：现行（2026-11-11 凌晨）。视角：不看代码有无 bug，只看**产出能不能用**。
> 方法：用 10 条覆盖真实场景的多样化输入（正常 / 短 / 垃圾 / 模板 / 重复 / 混语）灌入真实 DB，逐项量产出。

## 总评

| 维度 | 结论 | 量化 |
|---|---|---|
| **MCP 工具可靠性** | ✅ 良好 | 14/14 通过：10 类非法输入全部结构化报错不崩溃；20 并发写入 20/20 成功且无重复 id；重复 capture 去重返回同 id；检索结果确定性稳定；未知工具安全报错 |
| **存入机制** | ✅ 良好 | 去重准确（同内容→同 id，0 重复 hash 组）；并发安全；短文本正确拒收（`[短文本]` 被 rejected） |
| **人类可读性（content）** | ⚠️ 基本可用但有漏洞 | 8 条入库中 7 条可读；1 条不可读却入库（`ABC-123-XYZ-999`）；JSON 垃圾被"美化成" `a=1，b=2，c=3...` 后入库 |
| **记忆质量（门禁实效）** | ⚠️ **门禁只是标注，不是拦截** | 6 条标记 `review` 的记忆中 **5 条仍可被正常检索**——即低质量内容照样进入检索结果 |
| **subject 质量** | ❌ 明显不足 | 8/8 带机械前缀 `[L4 会话]老陈: `；6/8 在 60 字符处硬截断（丢句尾标点）；1 条残留模板 `{{...}}` |

## 关键发现（按严重度）

### 1.【重要】质量门禁 gate=review 不阻断检索
`review` 语义上意味着"待人工复核"，但实测这些记忆在 `search` 中与其他记忆同等可召回（5/6 命中）。
- 影响：质量门禁退化为**装饰性标签**。用户搜到的结果里会混入 `a=1，b=2…` 这类被"美化"过的垃圾。
- 期望行为（建议）：`review` 默认从检索中排除（或排名大幅降权），提供 `include_review=True` 显式查看；或至少把它们放到结果末尾并标注。

### 2.【重要】不可读内容仍会入库
`ABC-123-XYZ-999` 被 `_is_human_readable_content` 判为 `no_sentence_structure`，但 `gate=review` 仍写入库并被检索到。
- 期望：`no_sentence_structure` 且无法归一化的内容应**拒绝入库**（`quality.auto_reject_unreadable` 已有开关，但默认 `False`）。

### 3.【中等】JSON 垃圾被"美化"成 pseudo-内容
`{"a":1,"b":2,"c":3,"d":4,"e":5,"f":6}` → `a=1，b=2，c=3，d=4，e=5`，且被判 `可读=True`。
- 这是归一化函数的副作用：把结构化数据转成了"看起来像句子"的键值串，反而骗过了可读性检查。
- 期望：纯 JSON 应识别为结构化数据，要么原样保留并标 `kind=json`，要么拒绝；不应伪装成自然语言。

### 4.【中等】subject 机械前缀 + 硬截断
所有 8 条 subject 都是 `[L4 会话]老陈: ` + 内容截断。
- 前缀是级别/会话元信息，却塞进了本应**人类可读摘要**的字段；列表展示时全是同一前缀，可辨识度极低。
- 60 字符硬截断丢句尾（`...1000 QPS` 被切成 `...限流 1`）。
- 期望：subject 用 `_make_subject`/`_smart_subject` 生成语义摘要（如"PostgreSQL 主库选型"），不要回填 content 前缀；元信息放 metadata。

### 5.【轻微】模板泄漏仅标 review 不处理
`{{user_name}} 于 {{date}} 提交了...` 入库且可检索，subject 还残留 `user_name}} ...`（左侧 `{{` 被切掉，反而更难看）。

## 做得好的部分（确认可用）

- **MCP 工具可靠性扎实**：10 类异常输入（空 content、缺 action、未知 action、非法 level、超长内容、非数字 id、不存在 id、空 query、未知 mode、空 kb_ingest）**全部返回结构化错误、无一崩溃**。
- **并发安全**：4 线程 × 5 条 = 20 条并发写入全部成功，id 无重复。
- **去重有效**：相同内容重复 capture 返回同一 id。
- **检索确定性**：同 query 连续 3 次结果完全一致。
- **检索质量**：精确词/概念/中英混合 query 均能命中正确记忆；不存在的词正确返回 0 条。
- **正常内容质量好**：真实决策/偏好/事实类输入 quality 分 5.4–6.9，`accepted` 的那条 6.88 分。

## 结论

- **MCP 工具可靠性**：可以放心用（异常处理、并发、幂等、确定性都过关）。
- **存入机制**：去重与并发没问题；但**准入门槛实效不足**（review 不阻断）。
- **人类可读性**：content 基本可读，但**不可读内容会漏进来**，JSON 还会被"美化"伪装。
- **记忆质量**：**这是最大的短板**——门禁只标注不拦截，导致低质量记忆实际污染检索结果；subject 字段几乎不可用。

## 建议优先级

1. **P0**：`review` 状态默认不参与检索（或强降权）+ 提供显式开关——这是"记忆质量"最直接的杠杆。
2. **P0**：`no_sentence_structure` 无法归一化时拒绝入库（或至少不入检索）。
3. **P1**：纯 JSON / 模板识别为结构化数据，不伪装成自然语言。
4. **P1**：subject 改为语义摘要，去掉机械前缀。
5. **P2**：模板泄漏的清理规则。

> 注：本条为**结果验收**结论，未改动任何代码。若要按此修复，需明确 review 的检索策略（会影响现有消费方），建议先定策略再动手。
