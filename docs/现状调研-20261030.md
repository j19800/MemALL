## 三、测试面

```
python -m pytest tests -q
→ 见 §3.1（真实结果，附耗时）
```

### 3.1 pytest

**2026-10-30 在 `e5e2136` 上完整跑过一次：506 passed / 6 failed / 2 skipped，273 s。**

在 `4fae9a4` 上复跑没跑完，如实记录：同样测试集跑到 3% 用了 7 分钟，跑满预计数小时，本次中止、不给数字。

慢的原因不是玄学，是 `tests/conftest.py` 的 `_test_db`：**每个用例新建库 + `init_db(migrate=True)` 重放全部 48 条迁移**。48 × 512 ≈ 24,576 次迁移。隔离是对的，代价是线性膨胀；再叠上 migration 数量继续增长，全量测试迟早会变成"跑不起"。这是设计债，不是某个用例的错。

单独跑能复现的红灯（19 个用例 20.4 s 跑完）：

| 用例 | 现象 | 根因 |
|---|---|---|
| `test_gateway.py::test_gateway_capture` | HTTP **500** | 用例用了 `gateway_test` 这个身份，而它在生产 `security.disabled_agents` 里；`thin_waist.py:853` 抛 `capture: agent 'gateway_test' is disabled` |
| `test_gateway.py::test_api_graph_center` | HTTP **500** | 同一 deny-list 连带 |

这组红灯里藏着两件事，比"测试挂了"重要：

1. **语义错了**：策略拒绝（身份被禁用）被网关包成 **500**，正确的应是 **403**。500 意味着"服务端崩了"，会污染错误率指标，也会让调用方去重试一个永远不会成功的请求。
2. **绿不等于写成功**：同批跑结尾，后台线程抛了 `sqlite3.IntegrityError: NOT NULL constraint failed: memories.confidence`——`thin_waist.py:1398` 直接写 `data.confidence`，为 `None` 时绕过了列定义里的 `DEFAULT 0.5`，于是撞 NOT NULL。它在后台线程里发生，用例照样绿。**这是一条会静默丢写入的路径。**

### 3.2 守卫（`src/check_fixes.py`，90 条）

在 `e5e2136` 上的一次完整跑：**83 PASS / 2 FAIL，另有 4 个 suite 全 PASS**。两条失败要分开定性，它们不是一回事：

| 守卫 | 定性 | 根因 | 修法 |
|---|---|---|---|
| `busy_timeout_survives_concurrency` | **真缺陷（新代码）** | `pipeline/skills.py:159` 与 `:207` 用的是裸 `BEGIN`（DEFERRED）。事务从读锁升级写锁时，SQLite **不会**等 `busy_timeout`，直接返回 `SQLITE_BUSY` | 两行改成 `BEGIN IMMEDIATE`。这是当前唯一挡在"守卫全绿"前面的硬阻塞 |
| `metadata_cas` | **测试隔离问题** | 单跑通过，全量跑被前序用例的全局状态污染 | 守卫之间要重置全局状态；不是产品 bug |

**关于 4fae9a4 上的复跑，如实交代**：本次在 22:00 起跑，15 分钟后仍没出第一条 PASS——因为每条守卫都 `init_db()` 重建库、重放 48 条迁移，单条就要几十秒到一分钟，全量以小时计。**这本身就是结论**：一套要跑一小时的守卫，不可能被当作提交门槛；它现在的实际用法只能是"想起来才跑"，而这正是 `BEGIN` 缺陷能合进主线的原因。

这条 `BEGIN` 值得单独说一句：它说明**技能层合入时没有跑过并发守卫**。守卫存在但没被当作合入门槛——这比缺陷本身更值得改流程。

### 3.3 测试在污染生产

`~/.memall/metrics.jsonl` 的尾部是测试数据：

```json
{"total_memories": 8,  "total_edges": 4, ...}
{"total_memories": 4,  "total_edges": 2, ...}
```

全库约 5,670 条记忆，`total_memories: 8` 只可能来自测试。测试没有隔离 `MEMALL_HOME` 或指标路径，于是**每次跑测试都往生产观测文件里写垃圾**，任何基于 `metrics.jsonl` 的趋势分析都是假的。

### 3.4 守卫跑一轮的副作用

`check_fixes.py` 里 `tempfile.mkdtemp()`（:47、:272、:2992、:3520、:3556）**从不 `rmtree`**。跑一轮就在磁盘上留几十个含多份 2.5 MB 库副本的目录。详见 §七。

## 五、运行时面（心跳其实在跑——这是本次调研最重要的一次自我更正）

**先纠正一个容易得出的错结论。** 四条 OS 计划任务确实全部禁用：

```
memall-mcp-http        Disabled
MemALLBotFullAuto      Disabled
MemALL_Forget          Disabled
MemALL_Pipeline        Disabled
```

如果只看这里，结论会是"心跳早就停了"。**这个结论是错的。** `agent_round()` 的确只有 `scheduler/scheduler.py:112` 一个调用点，但另一条完全独立的驱动活着：

```python
# src/memall/mcp/server.py:158-161
from memall.pipeline.fallback import start_fallback_timer
start_fallback_timer(interval=300)
```

MCP server 初始化时会在**进程内**起一个 300 s 的 `FallbackTimer` 线程（`pipeline/fallback.py:307-350`），每个周期调 `run_fallback_once()` → `deliver_goal_prompts()` → `goal_tick()` → 向 agent 推 `goal:*` 会话通知。

线上证据不是推测，是记忆本身：今天每 15–30 分钟一条 `系统 · 管线观察（2026-10-30）` 的 L9 记忆，`pipeline.log` 停在 8 月但 `mcp_stderr.log` 今天一直在写。

**所以真实的因果链是：**

```
MCP 进程活着 → fallback timer 每 5 分钟 tick → goal_tick() 查库
                                              → 库里 0 条 goal 行
                                              → 没有任何 action 可发
                                              → 0 条 goal:* 通知
```

断点在**输入**，不在驱动。这也解释了 §4.2 里那个刺眼的 0：我们一直在给"通道"做体检，而通道一直是通的。

其他运行时事实：

- **20 个 `python` 进程**，其中至少 6 个 `memall.mcp.server`、2 个 `memall_bus.py`、1 个 `memall serve`。每个 MCP 进程都自带一个 fallback timer，**每 5 分钟就有 6 个并发 tick**；互斥只靠 `claim_run`（900 s）和会话通知的 dedup key 兜。这不是 bug，但"多进程各跑一个心跳"意味着节拍数 = 进程数，进程越多越吵。
- 总线在线（proto 2，inbox 0）。**但总线进程不在任何启动/保活流程里**，靠手工 `python memall_bus.py`，机器重启即失联。
- MCP stdio server 由每个客户端各 spawn 一个，长会话不退出就长期挂着——孤儿进程的源头，也是 tick 数量随会话数增长的源头。

一句话：**心跳不是没通电，是电网在转、下游没接负载。**

## 九、三个判断（结论在后，证据在前）
